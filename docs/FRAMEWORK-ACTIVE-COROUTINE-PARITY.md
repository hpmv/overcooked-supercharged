# Active coroutine rewind scope

The findings are grounded in the readable source under `H:/tiny2/Overcooked2/tinyoc2/Assets/Scripts/Assembly-CSharp` and checked against installed game metadata. `artifacts/framework-native-coroutine-layout.json` pins game SHA256 `9bb6a3791331201d32ca89c3509f019a9780309da7110002f04020e8491e1908`, MVID `114d606a-29d5-472c-8ebe-c2c20fbe3be3`, and the exact generated iterator field layouts. An experimental steady-flight sidecar is now implemented in `NativeCannonFlightCheckpoint.cs` and integrated with `NativeCannonCheckpoint`; **native midflight admission and continuation remain untested**. The headless active-cannon authoring gate remains a separate restriction.

**A steady mid-flight cannon checkpoint is the smallest plausible next scope.** `ClientCannon.UpdateSynchronising` directly advances its `m_launches` list, rather than passing these iterators to Unity's coroutine scheduler. `LaunchProjectile` nests `ProjectileAnimation.Run`, whose stored fields include elapsed time, start/target poses, curve duration and heights. After that iterator finishes, native `Land` applies the landing impact, `EndCannonRoutine` clears server flight and resumes synchronization, and `ExitCannonRoutine` waits for client synchronization readiness.

The implementation accepts exactly one flight iterator with its animation already running, no active server/client session, no pending interaction-end callback and no loading/unload/exit-wait transition. It captures an immutable managed clone of only the installed `ClientCannon/<LaunchProjectile>c__Iterator1` and `ProjectileAnimation/<Run>c__Iterator0` graphs, including `$PC`, current/disposal fields and every captured value. Restoration creates another fresh clone without running `MoveNext`, preserving pinned references and rejecting destroyed passenger/component incarnations. Unexpected generated fields/types or non-null yield objects reject capture. Ordinary native updates subsequently advance the restored iterator. A saved supported flight may be restored from a settled cannon or the same passenger's supported flight; restoring a saved settled cannon while a flight is active remains rejected.

Cloning the iterator alone is insufficient. The same snapshot needs exact passenger/carry/parent identity; server/client cannon messages and ready/flying flags; player handler `m_controls`, provider and `m_inCannon`; control enabled/switching flags; native collider/kinematic state; dynamic-landscape parenting enabled state; paused world synchronization and its resume predicates; and cosmetic/Animator state that can emit gameplay triggers. The existing generic warp must not end/recreate the session or fire callbacks while restoring this path. Native `Land`, impact and resume callbacks must each occur once at their original continuation frame. Native sessions themselves register mailbox callbacks and collision filters in their constructors, so invoking a constructor or `Load` to approximate an earlier state would repeat side effects.

**Delivered-plate fade needs a separate design.** `ClientPlateStation.DeliverPlate` calls Unity `StartCoroutine(DeliverySequence(...))`. That iterator disables colliders, may set a body kinematic, spawns PFX, yields `WaitForSeconds`, modifies renderer materials and increments private fade progress with `TimeManager.GetDeltaTime`, then destroys the plate. The managed iterator stores progress and renderer references, but the Unity scheduler owns the remaining wait time and scheduling position. The current `m_waitForPfxDelay` stores a duration object, not an elapsed-wait checkpoint.

An eventual bounded post-delay-only fade restore could track the exact iterator instance, stop that coroutine, restore cloned managed progress plus collider/material/body state, and restart it without replaying delivery/score callbacks. Its scheduler continuation timing still needs native proof. The PFX-delay phase additionally needs an observed remaining-wait clock and scheduler-boundary model; neither is presently captured. Replaying `DeliverPlate` would duplicate audio/PFX and reset the delay, and suppressing destruction would change native behavior. Keep the current pending-fade rejection until those states have explicit evidence.

Acceptance requires actual mid-flight and landing-boundary captures followed by the same recorded input tail twice, with per-frame iterator/cannon/control/sync/physics observations, exact landing/impact/removal frames and unchanged ledger. A successful inactive cannon restore does not establish this scope.

## Current source proof and remaining state

`artifacts/framework-cannon-iterator-tests.json` contains 21 checks of the production clone helper, including immutable repeated restores, exact reference aliasing, unknown yields and hidden managed state. `artifacts/framework-cannon-flight-state-tests.json` contains 20 checks of the production flight state-copy/restore/comparison methods using controlled registry/component/message stand-ins. `artifacts/framework-cannon-flight-source-contract.json` contains 31 installed-metadata and compiled-call checks, including the exact CLR2 target and generated native fields. The earlier checkpoint82 and dynamic42 suites also pass. These are offline tests; the component stand-ins do not establish Unity setter or scheduler behavior.

The flight sidecar copies the local passenger's client/server world and chef synchronizer fields, handler fields, selected control fields, dynamic parenting and `ChefLerp` fields. `ChefPositionMessage` and nested `WorldObjectMessage` values receive independent copies on capture and every restore. It pins other component/managed references. It does **not** copy every field reachable through those references, PhysX contacts/interpolation, all player/cannon material or particle state, or native input-receiver/transmitter history. Position-recorder history is retained rather than copied: native `RunCorrection` does not use it while paused, and local `ApplyResumeData` clears it before correction resumes. A native test must verify that this exact local-resume path actually occurs.

The absolute-clock issue needs a two-sided test. `ClientChefSynchroniser.ApplyResumeData` assigns raw `Time.time` to `m_ResumeTime`, and `RunCorrection` compares it to `m_ReceivedTimeStamp`. That timestamp comes from `ServerInputReceiver.GetLastClientInputTimeStamp`, which also uses raw `Time.time`; `ClientInputTransmitter` likewise stamps raw Unity time, and its server-local update returns early. Therefore the raw assignment alone does not prove a mixed-clock bug. The uncheckpointed receiver fields `m_LastReceivedTimeStamp`, `m_LastReceivedTimeStampServerTime` and `m_lastUpdatedTime`, and the relationship between their new raw-time epoch and restored chef synchronizer fields, must be observed through landing. Do not substitute the logical clock in only one of these methods. Separately, `NetworkTime` comes from native `ClientTime.Time`, whose logical source is restored by the existing clock sidecar.

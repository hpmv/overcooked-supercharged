# Paused native sleep-state audit

`artifacts/framework-native-q-sleep-audit.json` pins the closed Q idle-probe observations and retains every raw field difference. Baseline at gameplay frame181 and the first restored receipt match. The second restored receipt differs only in `sleeping` for bodies84,85 and110–122: baseline `true`, restored `false`. All15 have both raw and saved-resume `isKinematic=true`; the four chefs have saved-resume `isKinematic=false` and retain matching sleep flags. The original and both final replay raw-physics receipts match exactly in this idle fixture. The strict idle probe remains failed.

The source `TimeManager.FrozenPhysicsData` constructor stores linear/angular velocity, `isKinematic`, `useGravity` and layer. It then zeros velocities, sets kinematic true and disables gravity. `Unfreeze` restores those four physics values. It captures no sleep flag and calls neither `Sleep` nor `WakeUp`. Consequently, the existing frozen-state record cannot supply a missing "resumable sleep" value; inventing one would overstate the evidence.

Unity's frame loop continues during the game's layer pause: `TimeManager.Update` maintains timeScale1, while per-layer delta becomes0 and bodies become kinematic. PhysX therefore still receives paused wrapper ticks. The engine reports Unity2017.4.8 in its native log. PhysX3.3.4 describes kinematic sleep as dependent on a target pose and explicitly disallows its manual sleep/wake methods for kinematics. That is engine-level context, not a direct observation of Unity's private wrapper implementation. [PhysX3.3.4 rigid-dynamic API](https://docs.nvidia.com/gameworks/content/gameworkslibrary/physx/apireference/3.3.4/files/classPxRigidDynamic.html).

The observed timing is consistent with transient kinematic wake/target state after restore setters: the first restored receipt was five Unity frames after its preceding endpoint, while the second was four. Existing generic body setters and native freeze/unfreeze assignments remain candidates for that transient; the evidence does not isolate one setter as the cause. Since these15 bodies stay kinematic after resume and all final pose/velocity/flag values match, this is narrower than a demonstrated resumed dynamic-motion failure. It is still a real raw-state mismatch. `GroundCast.Update` also branches on `IsSleeping`, so sleep should not be dismissed for arbitrary dynamic chefs or other scopes.

The next bounded experiment should collect2–6 actual paused receipts with unchanged gameplay frame, exact Unity/fixed frame phase, all body poses/velocities/flags, and native round/food state. No moving input, logical-frame advance, explicit physics simulation or sleep-state setter is needed. If the exact saved sleep pattern naturally returns while every gameplay field remains unchanged, a future pause finalizer can wait for that specific captured state and acknowledge only after an exact match within a fixed callback bound. Such a finalizer must be recorded as an authoring boundary change and revalidated for phase alignment; it must fail if the state does not match. It must not overwrite the live reported sleep flags, exclude them from an unnamed comparison, or toggle kinematic mode to manufacture equality.

A generic finalizer calling `Sleep`/`WakeUp` after pause is not justified for this witnessed case. These calls can clear forces or reset wake timing, and native pause has already made even formerly dynamic bodies kinematic. Exact dynamic sleep/wake-counter restoration, if later required by a resumed-motion witness, needs its own pre-pause capture and native continuation test.
